> *"Fraud_Type 13개 클래스별 특징 파악을 위한 EDA 보완 필요. 현재는 13개 클래스를 함께 분석한 것으로 판단됨."*

**대응** — 이 지적이 이 프로젝트 통계 설계의 방향을 바꿨습니다.

13클래스 통합검정만 보면 정상 118,800건이 표본을 지배해 **거의 모든 변수가 negligible** 로 나옵니다.

| 변수 | 13클래스 통합 (ε²) | 정상 대비 이진 (Cliff's δ) |
|---|---|---|
| `Distance` | 0.0022 negligible | `a` 유형 **0.95 large (전체 최댓값)** |

### A-2. 확신도 판단 근거가 불명확 ✅

> *"유형별 특징 규명의 확신도 판단에 대한 근거를 구체적으로 제시 필요. 높음/중간/낮음을 나누는 기준 보완."*

**대응** — 주관 서술을 **계산 가능한 규칙**으로 바꾸고, 그 규칙으로 12유형을 전부 재분류했습니다.

```
높음 = Recall ≥ 0.7  AND  다른유형혼동율 ≤ 0.10
낮음 = Recall < 0.4  OR   다른유형혼동율 > 0.25
중간 = 나머지
```

| 등급 | 유형 | EDA 단계 대비 변동 |
|---|---|---|
| 높음 (3) | `a` · `f` · `h` | EDA 에서 '높음'이던 `b`·`c`·`e` 중 `c`·`e` 강등 |
| 중간 (5) | `b` · `k` · `i` · `e` · `j` | |
| 낮음 (4) | `d` · `g` · `c` · `l` | `c` 는 EDA '높음' → 실측 Recall 0.259 로 **낮음** |

**주목할 점** — EDA 신호가 강했던 `c`(단말 악성행위 전부 상승)가 실제 모델에서는 Recall 0.259 였습니다.
**신호가 보이는 것과 모델이 그걸 쓸 수 있는 것은 다르다**는 것이 이 재분류의 핵심 결과입니다.

### A-3. 단일 모델의 구조적 한계 → 규칙 기반 + ML 결합 권장 ❌ **검증 후 미채택**

> *"데이터가 극단적으로 불균형한 상태에서 단일 모델만으로 모든 클래스를 분류하는 것은 한계점이 있음.
> 필요에 따라 규칙 기반 알고리즘과 ML 모델 결합 시도 권장."*

**대응** — **권고대로 구현했고, 이득이 없다는 것을 수치로 확인한 뒤 채택하지 않았습니다.**

atom 181개(검증 파생 + 범주형 + 연속형 분위수)를 유형별로 2~3개씩 전수 조합해
최고 precision 규칙을 찾고, `override` / `boost` 두 방식으로 결합했습니다.

| precision 기준 | 채택 규칙 | override ΔF1 | boost ΔF1 |
|---|---|---|---|
| 0.85 | 1개 | **−0.0040** | 0.0000 |
| 0.70 / 0.50 / 0.30 | 3개 | −0.0040 | −0.0040 |

**왜 안 되는가** — 유형별 최고 달성 가능 precision 을 보면 명확합니다.

```
a  0.933   ← 유일하게 쓸 만함
b  0.211   c  0.105   d  0.062   e  0.167   f  0.200
g  0.074   h  0.172   i  0.096   j  0.069   k  0.133   l  0.118
```

사기 비율 1.08% 의 극단 불균형에서 단순 조건 조합으로는 정밀도가 나오지 않습니다.
게다가 유일하게 쓸 만한 `a` 규칙은 **ML 이 이미 Recall 0.957 로 잘 맞히는** 유형이라 보탤 것이 없습니다.

### A-4. `Amount_vs_monthly_max_ratio` — look-ahead 오류 ⚠️ **부분 대응 · 논란 남음**

> *"거래 시점에는 해당 월이 종료되지 않아 '월간 최대 거래 금액'을 확정할 수 없음.
> 미래 데이터를 참조하는 논리적 오류를 발생시킬 수 있으므로, 실제 시스템 운영 환경을 고려하여
> 산출 방식(예: 전월 기준 또는 현재 시점까지의 누적 최대값 등)에 대한 재검토 필요."*

**가장 뼈아픈 지적입니다.** 이 피처는 SHAP 5위(0.2288)이고 EDA 에서 "최상위 판별 변수"로 꼽혔습니다.

**팀의 대응** — 데이터 명세서상 해당 컬럼이 **"거래 기준 1개월 이전"** 을 의미한다고 해석하고 유지.

**그러나 완전히 닫히지 않았습니다.** 통합분석 코드가 실행할 때마다 경고를 띄웁니다.

```
[경고] look-ahead 의심 피처 잔존: ['Account_one_month_max_amount', 'Account_one_month_std_dev',
       'Account_dawn_one_month_max_amount', 'Account_dawn_one_month_std_dev',
       'Amount_vs_monthly_max_ratio']
       → as-of(시점까지 누적) 재설계 여부 전처리팀 확인 필요
```

즉 **팀 스스로 "명세 해석으로 유지했지만 확정은 아니다"** 라고 코드에 남겨 둔 상태입니다.
`LOOKAHEAD_SUSPECT` 리스트가 소스에 상수로 박혀 있고, 최종 요약에도 `⚠️ look-ahead 잔존: 5개` 가 출력됩니다.

**남은 일** — `as-of` 재설계 후 재측정. 5개 피처 중 2개가 SHAP 상위 10위 안이라
제거 시 성능 변동이 클 것으로 예상됩니다.

### A-5. 파생변수 근거가 순환논리 ✅

> *"전 항목의 서술이 '재확인', '스토리 보강', '가설을 계산 가능한 형태로 구현', '사실상 확정'으로 되어 있음.
> 이는 라벨을 이미 아는 전체 데이터에서 피처를 설계하고, 같은 데이터에서 잘 분리된다는 걸 근거로 채택하는 구조임.
> 진짜 근거가 되려면 (1) 시간 분할/홀드아웃/CV 에서의 lift, (2) 실제 모델에서의 feature importance / SHAP 기여도가 있어야 함."*

**대응** — 두 가지를 모두 붙였습니다.

| 요구 | 대응 |
|---|---|
| (1) 홀드아웃 lift | `StratifiedGroupKFold` 80/20 홀드아웃 **23,860행**에서 전 지표 재산출. 1차 EDA 는 `df_tr` 에서만 수행하도록 코드에 원칙 명시 |
| (2) SHAP | `TreeExplainer` (표본 2,000행) 상위 15피처 산출 → 파생 3종이 상위권 진입 |

SHAP 결과가 EDA 추정을 **확인해 준 것**과 **뒤집은 것**이 둘 다 있습니다.

| 유형 | EDA 추정 | SHAP 실측 |
|---|---|---|
| `c` | 단말 악성행위 전부 상승 | ✅ 확인 — 악성행위 6,2,5,4,3 전부 상위권 |
| `d` | "고유 신호 없음" | ❌ **뒤집힘** — `Channel`·`Access_Medium` 최상위. 신호는 있었다 |
| `g` | 고액입금 | ✅ 확인 — `Flag_deposit_more_than_tenMillion` 최상위 |
| `l` | 출생년도 집중 | ⚠️ 신호는 압도적 1위인데 **Recall 0.048** — few-shot 한계 |

**`l` 유형이 핵심 발견입니다.** 신호(`Customer_Birthyear`)는 뚜렷한데 학습 샘플 100건으로는
모델이 충분히 가중치를 못 줍니다. 이것이 "다음 과제: `l` 유형 보강"의 구체적 근거가 됐습니다.

### A-6. 모델 비교 단계에서도 비용을 반영해야 ⚠️ **부분 반영**

> *"분석 목표 및 문제 정의에서 비용 비대칭 구조가 핵심임을 강조했으나, 실제 모델 비교 과정에서는
> 모델 성능 기준으로만 비교하고 있음. 비용 기반의 최적화를 수행한다면 모델 비교 단계에서도
> 비용을 반영해서 비교하는 것이 타당함."*

**대응** — 모델 비교표에 **미탐(FN) · 오탐(FP) 건수를 함께** 실었습니다.

| 모델 | 임계값 | Macro-F1 | 미탐 | 오탐 |
|---|---|---|---|---|
| 한방 (argmax) | — | 0.6138 | 59 | 1 |
| 한방 + 임계값 | 0.03 | 0.6395 | 37 | 17 |
| 2계층 | 0.5 | 0.6105 | 43 | **51** |

FN/FP 를 병기하면 기대비용은 그 자리에서 계산됩니다.
2계층은 Macro-F1 이 낮으면서 오탐이 51건으로 3배라 **비용 기준으로도 열위**입니다.

**⚠️ 남은 부분** — 비교표에 **기대비용(억) 열 자체는 없습니다.** 임계값 파트에서만 계산합니다.
FN/FP 를 병기해 계산 가능하게는 했지만, 튜터가 요구한 "모델 비교 단계에서 비용으로 비교"를
표 한 장으로 보여주지는 못했습니다.

### A-7. trade-off 관계 — 각각 구체적 임계값 필요 ✅

> *"'정상 고객을 과도하게 막지 않는다'와 '13개 사기 유형을 정확히 탐지'는 trade-off 관계가 될 수 있음.
> 각 문제의 구체적인 임계값 설정이 필요."*

**대응** — **이중 임계값** 구조로 두 목적을 분리했습니다.

| 임계값 | 값 | 목적 | 동작 |
|---|---|---|---|
| `th_review` | **0.005** | 놓치지 않기 (미탐 최소화) | Slack 통보 — 사람이 본다 |
| `th_confirm` | **0.90** | 과차단 방지 (확실한 것만) | Slack + **Email** 승격 |

**하나의 임계값으로 두 목적을 만족시키려 하지 않은 것**이 이 설계의 요점입니다.
낮은 임계값은 "일단 사람에게 보여준다", 높은 임계값은 "정식 대응을 시작한다"로 역할이 다릅니다.

### A-8. ML 이 유일한 수단이 아님 ✅

> *"문제 해결의 핵심은 13개 사기 유형을 탐지하는 것이지, 13개 사기 유형을 탐지하는 최고의 모델을
> 만드는 것이 아님. 즉, ML 모델이 13개 사기 유형을 탐지하는 유일한 수단이 아님을 유의할 것."*

**대응** — 최종 시스템에서 ML 은 **여러 층 중 하나**입니다.

```
① ML 추론          LightGBM 13-class          risk = 1 − P(m)
② 규칙 체크        rule_checker.py            모델↔규칙 불일치 표시
③ LLM 분석         llm_analyzer.py + RAG      판정 근거 · 오탐 체크
④ 사람 판정        관제 콘솔 트리아지          정탐/오탐/미탐/보류
⑤ 피드백 루프      review_store → 임계값 튜닝  판정이 임계값을 되먹인다
```

**⑤가 이 피드백에 대한 가장 직접적인 답입니다.** 담당자 판정이 쌓이면
검증셋이 아니라 **실제 운영 분포 기준**으로 임계값을 다시 정할 수 있습니다.

### A-9. 운영 환경에서는 정답을 실시간으로 알 수 없다 ✅ **가장 크게 반영된 지적**

> *"실제 이상거래 탐지 시스템(FDS)이 가동되는 환경에서는 특정 거래의 이상 여부를 즉각적으로
> 판별하기 어렵다는 제약이 있음. 따라서 정답을 실시간으로 알 수 없는 운영 상황에서 해당 모델이
> 어떻게 적용되고 작동할지에 대한 구체적인 시나리오 설계 보완 필요."*

**대응** — 이 지적 하나가 **관제 콘솔(`ops_dashboard.py` 3,554줄) 전체의 존재 이유**입니다.

| 운영 제약 | 시스템의 답 |
|---|---|
| 정답을 모른다 | 담당자가 **정탐/오탐/미탐/보류**를 찍는 트리아지 큐 |
| 판정 기준이 바뀐다 | 판정 시점의 **임계값·모델·마스킹 레벨 스냅샷**을 함께 저장 |
| 미탐은 화면에 안 올라온다 | 큐는 *알림이 나간 건*만 담는다 → **거래 ID 직접 등록 창구** 신설 |
| 임계값을 바꿔도 되나 | 실제 판정 기반 **what-if 시뮬레이터** (선택 편향 구간 회색 표시) |
| 왜 그렇게 판정했나 | 탐지 시점 LLM 근거·확률·RAG 문서를 **분석 캐시**에 보존 |
| 사흘 뒤에 봐도 되나 | 원장은 **append-only** — 재탐지가 이전 판정을 덮어쓰지 않는다 |

> **미탐 등록 창구**가 특히 이 지적의 직접적 산물입니다.
> 트리아지 큐는 정의상 *알림이 나간 건*만 담으므로, 미탐(알림이 안 나간 건)은 화면에 올라올 경로가
> **아예 없었습니다.** 집계의 미탐 칸이 늘 0이었던 건 미탐이 없어서가 아니었습니다.
> 이제 `📉 오탐 분석`에서 거래 ID 로 직접 등록하면
> *"이 거래는 0.0031 < 임계값 0.005 라 알림이 안 갔습니다"* 까지 보여줍니다.

### B-2. 유형당 100건은 극소 표본 — 대안 필요 ❌ **대안 제시했으나 실패**

> *"각 사기 유형 100건(0.083%)은 극도로 작은 표본입니다. 유형당 100건에서 나온 배수·중앙값은
> 우연 변동에 취약합니다. 이에 대한 대안이 조금 필요해 보입니다."*

**팀의 대안** — CTGAN 등 생성 AI 합성데이터.

**결과** — **세 방식 전부 성능이 떨어졌습니다.**

| 방식 | Macro-F1 | ΔMacro-F1 |
|---|---|---|
| baseline (증강 전) | **0.6230** | — |
| +CTGAN | 0.5302 | **−0.0928** |
| +TVAE | 0.5859 | −0.0371 |
| +SMOTE (참고) | 0.5764 | −0.0466 |

**원인 — 대안이 같은 문제에 걸렸다.** 생성모델이 학습할 원본이 유형당 100건뿐이라,
만들어낸 500건은 원 분포를 재현하는 대신 **100건의 우연한 특성을 증폭**합니다.
CTGAN 이 가장 크게 무너진 것(−0.0928)이 그 방증입니다.

> **few-shot 문제를 few-shot 데이터로 푸는 방법은 없다** — 이것이 이 실험의 결론입니다.
> 멘토의 지적은 유효했고, 팀이 제시한 대안이 유효하지 않았습니다.
> 개선 방향은 데이터 증강이 아니라 **피처 품질(전처리)** 쪽이라는 것이 최종 판단입니다.

### B-3. "0.7103 이 어느 데이터의 수치인지 인지가 안 된다" ✅ **원인이 데이터 누수였다**

> *"group split 을 설계했으니 누수 통제는 돼 있을 텐데 0.7103 은 어디서 나온 데이터 수치인지
> 인지가 잘 안 되는 것 같습니다."*
> *"중간 결과의 0.7103 이 합성 데이터를 포함한 성능인지 아닌지가 안 보입니다.
> 합성 데이터를 train 에만 넣고 검증/테스트는 실제 데이터로만 했는지가 핵심입니다.
> 여기가 틀리면 성능이 부풀려집니다."*

**이 질문이 실제 버그를 찾아냈습니다.**

| | |
|---|---|
| **원인** | 통계 검정용으로 만든 `df`(= `train_binary`, `is_fraud` 포함)를 **파생변수 생성 이후까지 그대로 재사용** |
| **결과** | 정답 라벨 `is_fraud` 가 피처로 학습에 들어감 |
| **수정** | `df = train.copy()` 로 재시작 + `drop_cols_final` 에 `is_fraud` 방어적 추가 |
| **성능 변화** | **0.7103 → 0.6138 (−0.0965)** |

**합성 데이터 오염이 아니라 라벨 누수였습니다.** 멘토가 물은 두 가지 중 후자(합성)는 아니었고,
전자(어느 데이터인지)를 추적하다 진짜 원인이 나왔습니다.

**평가 독립성에 대한 답** — 증강 실험 코드 `ev(Xt, yt, Xv, tag)` 는 항상 원본 `y_va` 로만 채점합니다.
합성 데이터는 검증셋에 한 행도 들어가지 않습니다.

**재발 방지** — 통합분석 코드 상단에 라벨 자동 제거 가드를 넣었습니다.

```python
LEAK_COLS = ["is_fraud", "fraud_type", "label", "y"]   # 정답 라벨 자동 제거
_drop = [c for c in X_tr.columns if c.lower() in [s.lower() for s in LEAK_COLS]]
if _drop:
    print(f"[누수 제거] 정답 라벨 {_drop} 자동 제외")
```
