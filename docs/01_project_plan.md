# 01. 프로젝트 기획 — 계획과 실행의 대조

원본: [`reports/00_프로젝트기획서.pdf`](../reports/00_프로젝트기획서.pdf)

이 문서는 기획서를 요약하는 데서 끝내지 않고, **계획한 것 중 무엇이 그대로 됐고
무엇이 바뀌었으며 왜 바뀌었는지**를 함께 기록합니다. 포트폴리오에서 중요한 것은
계획의 정확도가 아니라 **계획이 틀렸을 때 어떻게 판단했는가**이기 때문입니다.

## 1. 프로젝트 개요

| 항목 | 내용 |
|---|---|
| 제목 | 실시간 이상거래 탐지 시스템 |
| 팀 | **쉽(10)네?** — 팀장 박근우 / 안영진 · 이태민 · 이혜진 |
| 기간 | 4주 (+ 시스템 확장 5주차 이후) |
| 데이터 | [DACON 금융 AI 챌린지](https://dacon.io/competitions/official/236297/data) — 한국 은행 전자금융 계좌이체 거래 |
| 규모 | 120,000행 × 64컬럼 · 13클래스 (`a`~`l` 사기 12종 각 100건 + `m` 정상 118,800건) |

### 문제 정의

> 정상 거래가 99%를 차지하는 극심한 불균형 속에서, **정상 고객을 과도하게 막지 않으면서**
> 13개 사기 유형을 정확히 탐지하고, 탐지된 이상 거래에 대해 실시간으로 알리고
> 대응 방안까지 자동 제시할 수 있는가?

### 왜 이 문제가 중요한가 (기획서 원문)

| 오류 종류 | 결과 |
|---|---|
| **미탐 (FN)** — 사기를 정상으로 통과 | 고객·은행에 직접적 금전 피해. **가장 치명적** |
| **오탐 (FP)** — 정상을 사기로 차단 | 정상 고객 이체 차단 → 불만·이탈·문의 폭증 |
| **유형 오분류** — 사기를 다른 사기로 | 잘못된 대응 절차 적용 → 사후 신고·처리가 꼬임 |

이 세 줄이 나중에 **비용 기반 임계값 설계**([`08_cost_based_threshold.ipynb`](../notebooks/team_final/08_cost_based_threshold.ipynb))의
출발점이 됩니다. 문제 정의에서 이미 "정확도 하나로는 안 된다"고 못 박은 것이 이 프로젝트의 축입니다.

## 4. 계획과 달라진 것 ① — n8n · MCP

기획서는 자동화 수단으로 **n8n**과 **MCP**를 지목했습니다. 최종 시스템에는 둘 다 없습니다.
**검토하지 않은 것이 아니라, 검토하고 뺀 것**입니다.

### MCP — 만들어 보고 뺐다

| | |
|---|---|
| 검증물 | [`notifier_mcp.py`](../notifier_mcp.py) — 프로토타입 구현 완료 |
| 판단 | **방향이 반대다.** MCP stdio 는 *사람이 Claude 를 통해 시스템에 말을 거는* 통로다. 필요한 것은 *시스템이 사람에게 먼저 알리는* 것 |
| 구조적 한계 | stdio = Claude Desktop 이 프로세스를 띄우고 도구를 호출하는 구조 → **상시 데몬(워처)이 호출할 수 없다** |
| 부수 발견 | 프로토타입이 `pipeline/notifier.py` 의 **복제본**이었다 (STARTTLS 폴백·오류 분류·`last_error` 진단이 빠진 구버전) → 로직 이중화 위험 |
| 결론 | 알림 경로에서 제외. **조회·질의 용도로는 적합** — "오늘 워처가 뭐 잡았어?"는 남은 과제 |

### n8n — 도입 조건을 정의하고 보류

지금 넣으면 **늘어나는 기능 0, 늘어나는 운영 부담 1**입니다. 탐지부터 발송까지가 이미 완결돼 있어
n8n 이 할 일이 없습니다. 대신 **언제 넣을지**를 못 박아 두었습니다.

| 도입 조건 (하나라도 생기면 즉시 검토) |
|---|
| **에스컬레이션** — 10분 내 담당자 미확인 시 팀장 전화 |
| **업무시간 라우팅** — 주간 Slack / 야간 SMS |
| **티켓 자동 생성** — Jira·Notion 에 대응 건 등록 |
| **승인 워크플로** — 계좌 정지 전 다단계 결재 |

붙이는 비용은 워처에 `--webhook-url` 옵션 하나입니다. 현재 하루 알림이 **2.8건**이라
라우팅 규칙이 필요한 규모가 아닙니다.

### 이 판단이 성립하는 이유 — 어댑터 구조

```
              pipeline/detect_service.py   ← 판정 엔진 (Streamlit 무관)
                        │
     ┌──────────┬───────┴────────┬──────────────┐
  대시보드      워처            (n8n용 API)     (MCP 서버)
   [완료]      [완료]            [미착수]        [프로토타입]
```

판정 로직을 `DetectService` 하나로 모았기 때문에 **이미 두 개의 어댑터가 같은 코어에 붙어 동작 중**입니다.
n8n·MCP 는 세 번째, 네 번째 어댑터일 뿐입니다. 복붙 구조였다면 어댑터를 늘릴수록 판정이 갈라졌을 겁니다.

> 상세 근거: [`기술선택_설명자료.md`](../기술선택_설명자료.md)

## 5. 계획과 달라진 것 ② — 모델 구조

| 기획서 예상 결과물 | 실제 | 왜 |
|---|---|---|
| **2단계 계층적 분류** (1단계 이진 → 2단계 유형) | ❌ **기각** | 1단계 FN 이 **영구 미탐**으로 굳는 오류 전파. 실측 Macro-F1 0.6105 로 한방 기본(0.6138)보다도 낮음 → [노트북 07](../notebooks/team_final/07_model_comparison_oneshot_vs_twostage.ipynb) |
| 13-class Baseline (비교용) | ✅ **본선 채택** — 한방 + 사후 임계값 조정 | 오류 전파 없이 임계값 유연성 확보 |
| **이상탐지(ISF) 점수 결합** | ⚠️ **부분 실행** | ISF 자체는 1주차에 실행됨(`reports/04` §3-3, PR-AUC 0.030). 다만 **'피처로 결합'** 은 미실행이었고, 이 저장소가 [노트북 11](../notebooks/team_final/11_baseline_and_anomaly_score.ipynb) 로 실측 → **−0.0084, 이득 없음** |
| CTGAN 합성 증강 | ✅ 실행 → ❌ **미채택** | CTGAN −0.0928 · TVAE −0.0371 · SMOTE −0.0466. 셋 다 성능 하락 → [노트북 10](../notebooks/team_final/10_synthetic_augmentation.ipynb) |
| 위험 점수 `1−P(m)` | ✅ 그대로 | 시스템 전체의 단일 판정 축 |
| 성능 평가 리포트 | ✅ 13×13 혼동행렬 · 클래스별 P/R/F1 | 노트북 06 |
| 오탐/미탐/오분류 분석 | ✅ + **운영 판정 기반 재분석**까지 확장 | 관제 콘솔 `📉 오탐 분석` 탭 |
| 예측 출력 인터페이스 | ✅ `DetectService.detect()` | Part C 로 그대로 연결 |

> **주목** — 계획서가 "예상 결과물"로 적은 2단계 구조를 팀이 **자기 손으로 반증**했습니다.
> 계획대로 하지 않은 것이 아니라, 계획을 검증해서 뒤집은 것입니다.
