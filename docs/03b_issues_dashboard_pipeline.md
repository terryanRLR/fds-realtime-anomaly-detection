## B-1. 🔴 번들 3파일이 joblib 인데 코드는 `pickle.load` → 전체 더미 모드

**증상**
세션5 예측이 **매번 랜덤**하게 나온다. 에러 메시지는 없다.

**재현 조건**
팀이 배포한 모델 번들을 `models/` 에 넣고 대시보드를 켤 때.

```
lgbm_13class(최종).pkl   pickle ❌ invalid load key '\x05'   joblib ✅
label_encoders.pkl       pickle ❌ invalid load key '\x0a'   joblib ✅
le_target.pkl            pickle ❌ invalid load key '\x08'   joblib ✅
```

**원인 진단**
`ml_classifier._load_all` 은 **모델 본체에만** joblib 폴백이 있었고, **메타 2파일은 맨 `pickle.load`** 였다.
그 `UnpicklingError` 가 바깥 `except Exception` 으로 전파되어 **번들 전체가 더미 모드**로 빠졌다.

> `invalid load key` 는 **버전 문제가 아니라 파일 형식 문제**다.
> 버전 불일치는 `ModuleNotFoundError`/`AttributeError` 계열로 따로 나타난다.
> 이걸 구분하지 못해 팀이 "sklearn 버전 때문"이라고 오진하고 있었다.

**해결**
`bundle_io.safe_load()` 신설 (pickle → joblib 순차 시도) 후 **6곳 교체**.

| 파일 | 영향 |
|---|---|
| `ml_classifier.py:109,111` | 🔴 더미 모드 → 정상 |
| `dataset_loader.py:229` | 라벨 디코딩 실패 → 세션2 F1 0 → 정상 |
| `dashboard.py:1176` | 세션3 세그먼트 디코딩 실패 → 정상 |
| `model_loader.py:289,310` | 클래스 복원 실패 (알파벳 폴백이 **우연히** 일치해 살아있었음) |

버전 불일치는 별도 `TypeError` 로 승격해 *"requirements 기준으로 버전을 맞추라"* 는 실행 가능한 안내를 낸다.

**근거** — [`PATCH_NOTES5.md`](../PATCH_NOTES5.md) §1-A · [`FIX_REPORT.md`](../기타%20문서/FIX_REPORT.md) v5.3

**상태** `✅ 해결`

## B-2. 🔴 범주형 9개가 입력과 무관하게 0으로 고정

**증상**
Channel 을 ATM 으로 바꾸든 Internet 으로 바꾸든 **예측 결과가 똑같다.**

**재현 조건**
새 `label_encoders.pkl` 을 쓰는 모든 단건 예측 경로.

**원인 진단**
새 인코더의 `classes_` 가 문자열이 아니라 **정수**다.

```python
Channel        → array([0, 1, 2, 3])
Customer_Gender → array([0, 1])
```

팀 전처리가 문자열을 먼저 인코딩한 뒤 **그 결과로 다시 `LabelEncoder` 를 fit** 한 결과다.

`_preprocess` 는 `str(raw).strip() in le.classes_` 로 비교했는데
`"1" in np.array([0,1,2,3])` 은 **항상 False**. 기본값도 `"1"` 이라 또 False → `data[col] = [0]`.

```
before:  Channel 0→0  1→0  2→0  3→0      (뭘 넣어도 0)
after :  Channel 0→0  1→1  2→2  3→3   ·  Gender 1→1  ·  Birthyear 1980→1980
```

**해결**
`is_numeric_encoder()` 로 "수치형으로 학습된 인코더" **45개**를 자동 감지 →
해당 컬럼은 인코딩을 건너뛰고 원본 수치를 통과.
문자 인코더 번들에는 기존 경로를 유지하고, 비교는 `[str(c) for c in le.classes_]` 로 dtype 무관하게 수정.

**근거** — [`PATCH_NOTES5.md`](../PATCH_NOTES5.md) §1-B

**상태** `✅ 해결`

## B-3. 🔴 정수 클래스 vs 문자 라벨 — 에러 없이 전 지표가 정확히 0.0

> **이 저장소에서 가장 교과서적인 '조용한 실패'입니다.**

**증상**
*"세션5 는 되는데 세션2 동적 평가만 실패한다."*
예외는 안 나고, **모든 성능 지표가 정확히 0.0** 으로 나온다.

**재현 조건**
`lgbm_fds.pkl` / `rf_fds.pkl` 처럼 **`y` 를 인코딩한 채로 fit** 한 모델을 세션2 동적 평가에 쓸 때.

**원인 진단**
두 모델 모두 48피처로 정상이지만 `classes_` 가 `'a'~'m'` 이 아니라 **정수 0~12** 다.

| 경로 | 동작 |
|---|---|
| 세션5 (`MLClassifier`) | `le_target.pkl` 로 정수→문자 복원 → **정상** |
| 세션2 동적 (`UnifiedModel`) | `model.classes_` 숫자를 그대로 사용 |

→ 예측이 `"0"`~`"12"`, 정답이 `"a"`~`"m"`.
**교집합이 공집합**이라 `f1_score` 가 예외 없이 0.0 을 반환한다.

> 0.0 은 "모델이 나쁘다"로 읽힌다. "배선이 끊겼다"로 읽히지 않는다.
> 그래서 팀은 몇 번이나 모델을 다시 학습했다.

**해결 3건**
1. **로더 정수 클래스 자동 디코딩** — pickle/joblib/번들 로드 시 `classes_` 가 숫자면
   `le_target.pkl`(우선) 또는 알파벳 매핑으로 `'a'~'m'` 복원. 세션5 와 동일 규칙으로 통일.
2. **평가기 안전망** — 예측 라벨(숫자) vs 정답(문자) 불일치를 감지하면 자동 매핑 + 화면에 노트 표시
   (*"정수 클래스→문자 디코딩"*). 향후 어떤 경로로 숫자 클래스가 들어와도 **0.0 위장 불가**.
3. ⚡ **배치 전처리 벡터화** — 행별 루프(5,000행 ≈ 수 분) → 컬럼 단위 일괄 인코딩 → **0.5초**. 결과 동일.

**검증**
- train.csv 동적: 수정 전 F1 전부 0.0 → 수정 후 정상 산출
- parquet:va 전량(23,860행): LightGBM F1 0.9022 / RF 0.8718

> ⚠️ **그리고 그 검증이 또 다른 문제를 드러냈다.**
> va 성능(F1 0.90)이 학습 리포트(`eval_result.json`, F1 0.5159)보다 크게 높다.
> 이 pkl 들이 **검증셋을 포함한 전체 데이터로 재학습된 버전**일 가능성이 크다.
> → 팀에 "va 로 성능을 인용할 때는 X_tr 만으로 학습된 모델인지 확인하라"고 공지.

**근거** — [`FIX_REPORT.md`](../기타%20문서/FIX_REPORT.md) v5.5

**상태** `✅ 해결 · ⚠️ 모델 재학습 의혹은 팀 확인 필요`

## B-4. 🔴 더미 모드에서 `risk` 가 역전 — 정상 예측이 전부 고위험

**증상**
모델 로드가 실패해 더미 모드로 빠진 상태에서, **이상 판정률이 100%** 로 나온다.

**재현 조건**
`ml_classifier` 더미 모드에서 예측 클래스가 `'m'`(정상)일 때.

**원인 진단**
더미 분기가 `P(m) = score` 로 넣고 있었다. `risk = 1 − P(m)` 이므로
score 가 낮을수록 risk 가 높아진다 — **정상 확신이 강할수록 고위험으로 나온다.**

**해결 + 검증 (3,000건 시뮬레이션)**

| 지표 | Before | After |
|---|---|---|
| 이상 판정률 | **100%** | 15.6% |
| `m` risk 평균 | **0.845** | 0.157 |
| `risk ≡ 1−P(m)` 오차 | — | **0** |

**근거** — [`FIX_REPORT.md`](../기타%20문서/FIX_REPORT.md) 🔴 Critical ①

**상태** `✅ 해결`

## B-5. 🟠 48피처 모델 × 81피처 데이터 — 피처 불일치

**증상**
```
number of features (81) != training (48)
feature names should match
```

**재현 조건**
48피처(원본 계열)로 학습한 모델에 81피처(전처리 완료 parquet)를 입력할 때, 또는 그 반대.

**원인 진단**
데이터셋과 모델의 **계열**이 다르다. 다만 검증해 보니 81피처 셋에
원본 48피처 중 **46개가 이름 그대로 포함**돼 있어 자동 매칭이 가능했다.

**해결 — 자동 피처 매칭 (evaluator v5.4)**
모델별로:
1. 모델이 기억하는 학습 피처명(`feature_names_in_`/`feature_name_`/Booster) 조회
2. 데이터셋에서 이름 기준 선택·재정렬 (sklearn 'feature names' 오류 해소)
3. 누락 피처(≤20%)는 `feature_defaults.json` 값으로 대체 + **화면에 노트 표시**
4. 누락 과다(>20%) = 계열이 다름 → **해당 모델만** 명확한 사유로 격리 (앱은 안 죽는다)
5. 피처명 없는 형식(ONNX)은 차원 검증 후 안내

**검증** — 48피처 lgbm/lr × 81피처 parquet 양쪽 평가 성공.
역방향(81피처 모델 × 원본 CSV)은 "35개 누락 — 계열 다름" 격리 + 나머지 정상.

> ⚠️ **대체된 피처는 상수가 된다.** 해당 모델 성능은 참고치이며,
> 정밀 비교는 계열 일치 데이터셋을 권장한다는 노트를 **항시 표시**한다.

## B-6. 🟠 팀 산출물이 단일 모델이 아니라 조립이 필요한 '세트'였다

**증상**
팀 모델 파일을 넣었더니 메타 pkl 이 "모델"로 목록에 뜨고, 고르면 예측이 깨진다.
2단계 모델은 단독으로는 13클래스 평가와 라벨 체계가 안 맞는다.

**원인 진단 — "모델 문제도, 시스템 버그도 아닌 구조 불일치"**

팀 산출물의 실제 구성:

| 부품 | 내용 |
|---|---|
| 메타 pkl 2종 (dict) | 피처 순서 81 · labels `a~m` · `normal_idx=12` · 임계값(0.5 / 미탐0 0.0003) · usage 규칙 |
| 모델 3종 | 한방 13클래스 / 1단계 이진 / 2단계 12유형 — 전부 **joblib 저장** |

즉 **단일 모델이 아니라 조립 설명서가 딸린 부품 세트**였다.

**해결 — 컴포지트 자동 조립**
1. 메타 pkl 감지 → `🧩 한방(메타결합)` / `🧩 2단계 파이프라인 · 미탐0` 으로 등록.
   부품(메타·1단계·2단계)은 단독 목록에서 **숨김**.
2. **2단계 의미 보존** — 예측 = usage 규칙 그대로
   (`risk = s1[:,1]`, thr 판정 후 s2 유형). argmax 가 아니라 `_predict_labels` 로 평가·배치에 반영.
   proba 는 `[정상 = 1−r, 유형 = r × s2]` 로 합성.
3. 메타의 `feature_cols`(81)를 자동 피처 매칭이 **최우선**으로 사용.

**검증 (parquet:va 23,860행)**

| 조합 | 결과 |
|---|---|
| 🧩 한방 | **F1 0.6828** ← 메타 기록 학습 시 valid F1 0.6854 와 사실상 일치 (**배선 교차검증**) |
| 🧩 2단계 (thr 0.0003) | 사기 258건 중 **미탐 1건** — '미탐0' 설계 의도 재현 |

> **F1 0.1499 는 결함이 아니라 재현율 극대화 운영점의 특성이다.**
> 2단계 세트는 애초에 "미탐을 0으로 만드는 대신 오탐을 감수한다"는 설계다.

**후속 버그** — 팀 파일명이 괄호였다: `2단계(2)(미탐0...)`.
`_match_part` 의 언더스코어 매칭이 실패해 컴포지트가 조립되지 않고 부품이 날것으로 노출됐다.

## B-7. 🟠 세션5 의 5가지 입력이 전부 원본 행 — 파생 모델을 못 쓴다

**증상**

단, **데이터 분포를 다시 만들 필요는 없었다.** 빠진 것은 분포가 아니라

81피처 분해:

| 종류 | 개수 |
|---|---|
| 원본 그대로 | 37 |
| 인코딩 맵 필요 | 9 |
| 행 단독 파생 | 32 |
| 학습 빈도표 필요 | 3 |

→ **전부 변환기 문제**이며, 원본 행 1건에서 계산 불가능한 정보는 없다.

**해결 2트랙**

**A. 정석** — 팀 전처리 코드를 fitted transformer(pkl)로 동봉. 100% 정확. (장기 권장)

**B. FeatureBridge** ([`pipeline/feature_bridge.py`](../pipeline/feature_bridge.py), 523줄)
전처리 코드 없이, 팀 환경에 이미 있는 **`train.csv`(원본) + `X_tr.parquet`(변환 결과)** 쌍에서

```
원리:  X_tr 인덱스가 원본 행 번호를 보존 → 정렬 후, 피처별로
       identity → 값 매핑(lookup: 인코딩·빈도표·시군구)

안전:  시작 시 정렬 자가검증 — 짝이 아닌 쌍은 명확히 거부 (검증: 26.7% → 거부)
```

**공식 역산 포렌식으로 복원한 팀 파이프라인 규칙**

| 피처 | 복원한 규칙 | 방법 |
|---|---|---|
| ratio 류 | **순수 나눗셈** (eps 없음, 0나눗셈 → inf) | 분모 역산 |

| `threat_total_count` | 6그룹 합 (단말악성6 + 인증변경4 + 루팅 + VPN + 미사용단말 + 로밍) | 잔차법 |

**최종 성적 (X_va 23,860행 완전 홀드아웃)**

| 항목 | 결과 |
|---|---|
| 피처 복원 | **78/81 이 99%+ 정확** |

## B-9. 🟠 NaN 대체가 macro-F1 을 0.7%p 깎고 있었다

**증상**
같은 모델·같은 데이터인데 대시보드 평가값이 노트북보다 낮다 (0.6070 vs 0.6138).

**재현 조건**
`make_batch_preprocess` 가 `feature_defaults` 로 NaN 을 일괄 대체할 때.

**원인 진단**
`X_va` 에 **진짜 NaN 이 2,196행** 있다.

| 컬럼 | 건수 | 원인 |
|---|---|---|
| `Amount_vs_monthly_max_ratio` | 2,195 | 분모 0 → 0/0 |
| `Time_difference_seconds` | 30 | 음수 → NaN 처리 ([`03a` #A-8](03a_issues_data_modeling.md)) |

LightGBM 은 NaN 을 **native 분기**로 처리한다. 학습 때 "이 값은 결측"이라는 정보로 학습했는데,
추론 때 기본값으로 채우면 **다른 신호를 준 것**이 된다.

```
keep_nan=True  (신규 기본) → macro F1 0.6138  ✅
keep_nan=False (구 동작)   → macro F1 0.6070  ← 조용한 손실
```

**해결**
`make_batch_preprocess(clf, keep_nan=True)` — **'컬럼 자체가 없음'과 '값이 NaN'을 구분**한다.
컬럼 부재는 기본값으로 채우고, 계산 결과 NaN 은 보존.
`keep_nan=False` 는 NaN 비허용 모델(LogReg/SVM/ONNX) 비교용으로 남겼다.

**근거** — [`PATCH_NOTES5.md`](../PATCH_NOTES5.md) §1-D

실측해 보니 진짜 원인은 둘이었다.

- 🏦 계좌 이력을 **UI 로 노출** + 되돌리기 버튼
- `AUTOFILL_PRESET` + `AUTOFILL_FLAGS` 로 자동채움 값 세트 통일 (합집합 5종)

**검증** — 두 앱이 같은 입력에 **같은 판정**: `d / 0.8773517059743291`.
`selftest_ui` §13 으로 고정.

> **진단이 틀렸다는 것을 실측으로 확인하고 고친 사례**입니다.

- Macro avg 캡션 추가
- 평가 **실패**한 모델을 F1 0.0 으로 위장하지 않고 **⚠ 오류 카드**로 구분 표시

추가로 v13 에서 **조용한 오예측 → 예외 승격** — 순서를 알 수 없으면 예측하지 않고 멈춘다.

## B-24. 🟠 포트폴리오 문서를 `docs/` 에 두면 RAG 지식베이스가 먹는다

> **이 저장소를 만들면서 발견한 이슈입니다.**

**증상 (발생 전 차단)**
`docs/` 에 기획서·이슈로그·튜터 피드백을 두면,
LLM 이 *"이 거래가 왜 이상한가"* 를 설명할 때 **기획서 문장을 근거 문서로 인용**하게 된다.

**재현 조건**
`pipeline/rag_searcher.py` 의 `DOCS_DIR` 기본값이 `프로젝트루트/docs` 였고,
임베딩 대상이 `DOCS_DIR.glob("*.md")` — **최상위 모든 `.md`** 다.

```python
for md_file in sorted(DOCS_DIR.glob("*.md")):   # ← 필터가 없다
    ...
self.collection.add(documents=docs, ids=ids, metadatas=metas)
```

`docs/01_project_plan.md` 를 두는 순간 그 내용이 벡터 DB 에 들어가고,
`chroma_db/.docs_sig`(mtime 해시)가 바뀌면서 **자동 재임베딩**까지 걸린다.

**원인 진단**
`docs/` 라는 이름이 두 가지 뜻으로 쓰이고 있었다.

| 관점 | `docs/` 의 의미 |
|---|---|
| 저장소 관례 | 사람이 읽는 프로젝트 문서 |
| 이 시스템 | **런타임 지식베이스** — LLM 이 인용할 사기 대응 매뉴얼 |

**해결**
운영 지식베이스를 `knowledge/` 로 분리하고 기본값 2곳을 바꿨다.

| 파일 | 변경 |
|---|---|
| [`pipeline/rag_searcher.py`](../pipeline/rag_searcher.py) | `DOCS_DIR` 기본값 `docs` → `knowledge` |
| [`tools/build_rag_docs.py`](../tools/build_rag_docs.py) | `--out` 기본값 `docs` → `knowledge` |

환경변수 `FDS_DOCS_DIR` 탈출구는 그대로 유지된다.
`knowledge/` 에는 원래의 3문서(`fraud_types.md` · `response_manual.md` · `rule_reference.md`)만 있다.

**확인**
```
DOCS_DIR = .../포트폴리오/4/knowledge
md files = ['fraud_types.md', 'response_manual.md', 'rule_reference.md']
```

> **RAG 지식베이스는 코드나 설정에 가깝지 문서가 아닙니다.**
> LLM 이 인용할 것과 사람이 읽을 것을 같은 폴더에 두면, 폴더에 파일을 하나 넣는 것만으로
> 판정 근거가 바뀝니다. **아무 에러도 없이.**

**상태** `✅ 해결 (이 저장소에서)`
