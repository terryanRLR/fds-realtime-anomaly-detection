## C-1. 🔴 같은 컬럼에 UTC 와 KST 가 섞여 들어간다

**증상**
오탐 대시보드에서 여러 테이블을 하나의 타임라인에 합치면 **9시간짜리 유령 피크**가 생긴다.

**재현 조건**
DB 전수 조사 결과, **테이블마다 시간대가 다르다.**

| 테이블.컬럼 | 쓰는 코드 | 시간대 |
|---|---|---|
| `watcher_status.started_at` / `last_poll` | `watcher.py:185,187` | UTC |
| `watch_cursor.updated_at` | `watcher.py:175` | UTC |
| `notified.sent_at` | `detect_service.py:668` | UTC |
| `detections.detected_at` | `detect_service.py:722` | **LOCAL** |
| `transactions.processed_at` (detect_service) | `detect_service.py:743` | **LOCAL** |
| `transactions.processed_at` (컬럼 DEFAULT) | `detect_service.py:600` | **UTC** ⚠️ |

**마지막 두 줄이 결정적이다 — 같은 컬럼에 UTC 행과 KST 행이 섞여 들어간다.**
코드가 명시적으로 쓸 때는 LOCAL, DEFAULT 로 채워질 때는 UTC.

**원인 진단**
각 테이블을 **따로** 보는 화면에서는 터지지 않는다. 상대 순서가 유지되기 때문이다.
관제 콘솔이 처음으로 이것들을 **하나의 타임라인에 합치면서** 드러났다.

**해결 — 두 겹**

1. **읽기 정규화** — 모든 조회가 [`pipeline/ops_queries.py`](../pipeline/ops_queries.py) 를 통과하며
   UTC 로 정규화되고, 화면 표시 **직전에만** 로컬로 되돌린다.
   `diagnose_timestamps()` 가 현재 오염 상태를 🩺 진단 탭에 보고한다.
2. **근본 수정** — `migrate_timestamps.py` (M001 마이그레이션) + writer 6곳 패치.
   `dashboard.py` 의 localtime writer 6곳 → UTC, 표시 1곳 보정.

```bash
python migrate_timestamps.py fds_results.db --apply
```

**팀 규칙으로 승격** — *"DB 는 UTC 로 통일돼 있다. 표시 시점에만 로컬로 바꾼다."*

**검증** — `selftest_ops` 가 **UTC 행과 KST 행이 섞인 DB 를 실제로 만들어**
정규화가 동작하는지 확인한다.

**근거** — [`pipeline/ARCHITECTURE.md`](../pipeline/ARCHITECTURE.md) §3.2 ·
[`pipeline/MIGRATION_RUNBOOK.md`](../pipeline/MIGRATION_RUNBOOK.md)

<a id="c-2"></a>
## C-2. 🔴 `strftime()` 이 TEXT 를 반환 — 비교가 항상 참이었다

**증상**
시간대 판별 로직이 **UTC 컬럼까지 LOCAL 로 오진**한다.

**재현 조건**
SQLite 에서 이런 비교를 할 때.

```sql
strftime('%s', col) > strftime('%s', 'now') + 60
```

**원인 진단**
`strftime()` 은 INTEGER 가 아니라 **TEXT** 를 반환한다.
SQLite 의 타입 서열은 `NULL < INTEGER/REAL < TEXT < BLOB` 이므로,
**TEXT > INTEGER 는 항상 참**이다.

즉 위 조건은 값과 무관하게 언제나 성립했다. **에러도 경고도 없다.**

**해결**
```sql
CAST(strftime('%s', col) AS INTEGER) > CAST(strftime('%s','now') AS INTEGER) + 60
```

**우연히 살아남은 코드가 있었다**
`watcher_panel.py` 는 같은 함수를 쓰면서도 멀쩡했다.
`CAST(strftime(...) - strftime(...) AS INTEGER)` 처럼 **뺄셈**을 써서
숫자 강제변환이 먼저 일어났기 때문이다.

> **비교 연산을 쓰는 순간 터지는 지뢰였다.** 뺄셈은 안전하고 비교는 위험하다 —
> 같은 함수인데 사용법에 따라 결과가 갈린다.

<a id="c-3"></a>
## C-3. 🔴 `detections` UPSERT 가 이전 판정을 조용히 덮어쓴다

**증상**
같은 거래가 다시 유입되면 **이전 탐지 기록이 사라진다.** 이력 추적이 불가능하다.

**재현 조건**
`detections` 테이블은 `transaction_id` 가 PK 이고 `INSERT ON CONFLICT UPDATE` 를 쓴다
(`detect_service.py:722`). 같은 거래를 재탐지하면 행이 갱신된다.

**원인 진단**
"최신 판정만 있으면 된다"는 설계였다. 탐지 결과만 볼 때는 맞다.
그러나 **사람의 판정은 감사 대상**이다. 누가 언제 무엇을 판정했는지가 덮어써지면 안 된다.

**해결 — 원장을 갈아탔다**

| 용도 | 테이블 | 이유 |
|---|---|---|
| **알림 원장** | `transactions` | `AUTOINCREMENT` · **append-only** |
| 피처 보조 | `detections` | `raw_json` 을 얻는 용도로만 |
| **판정 기록** | `alert_review` (신규) | **append-only** · 재판정하면 새 행 |
| 분석 캐시 | `analysis_cache` (신규) | **append-only** |
| 감사 로그 | `notify_audit` (신규) | **append-only** · 2단계 확인 삭제 |

**`alert_review` 설계 결정 2가지**

**① 추가 전용** — 판정을 `UPDATE` 하지 않는다. 재판정하면 새 행이 쌓이고 최신 행이 현재 판정이다.

**② 판정 시점 스냅샷 동봉** — 워처 임계값은 `watcher_config.json` 으로 **핫 리로드**된다.
`th_review=0.45` 에서 내린 "오탐"과 `0.60` 에서 내린 "오탐"은 **비교 불가**다.
스냅샷이 없으면 임계값 시뮬레이터가 전부 거짓말이 된다.

```sql
CREATE TABLE alert_review (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    txn_id TEXT NOT NULL, alert_ref INTEGER,
    verdict TEXT NOT NULL,          -- tp | fp | fn | unclear
    reason TEXT, memo TEXT, reviewer TEXT,
    -- 판정 '당시' 스냅샷
    tier, risk_score, fraud_type, th_review, th_confirm, model,
    source TEXT, reviewed_at TEXT NOT NULL   -- ⚠ UTC 고정
);
```

**팀 규칙으로 승격** — *"원장은 append-only. 조회는 반드시 `ops_queries` 를 거친다."*

<a id="c-4"></a>
## C-4. 🔴 LLM 분석 근거가 Slack 을 보내는 순간 사라진다

**증상**
사흘 뒤 담당자가 판정하려고 보면 **`위험 0.72, 유형 f`** 만 남아 있다.
왜 그렇게 판정했는지 알 수 없다.

**재현 조건**
`detect_service.detect()` 는 거래 1건마다 이만큼을 계산한다.

```python
det["proba"]   # 13클래스 확률 분포
det["llm"]     # {"analysis", "slack", "email", "ctx"}  ← LLM 리포트 전문
det["tier"] / ["errors"] / ["elapsed"]
masked         # 마스킹된 원거래 내역
rag_ctx        # RAG 근거 문서
```

그런데 `_save_db()` 가 남기는 것은 **6개 컬럼뿐**이다 —
`fraud_type` · `risk_score` · `is_anomaly` · `model` · `threshold` · `raw_json`.

**원인 진단**
> **LLM 이 쓴 판정 근거·이상 패턴·오탐 체크·권장 조치는 Slack 을 보내는 순간 사라진다.**
> LLM 을 돌리는 이유 자체가 그 분석인데 DB 에 한 글자도 남지 않는다.

재검증 경로도 막혀 있다 — 마스킹 훼손([C-5](#c-5)) 때문이다.
따라서 **탐지 시점에 캐시하는 것이 근거를 남기는 유일한 방법**이다.

**해결 — `pipeline/analysis_store.py` (501줄)**

워처에 **2줄**만 넣으면 된다.

```python
from pipeline import analysis_store as astore
astore.attach(svc)     # DetectService 생성 직후
```

`attach()` 는 인스턴스의 `detect` 를 감싸는 래퍼라 `detect_service.py` 나 `watcher.py` 본문은 손대지 않는다.

> ⚠️ **이 2줄만은 워처 쪽에 들어가야 한다.** 다른 모든 것은 기존 파일 수정 없이 붙였지만,
> LLM 리포트는 그 순간 **워처 프로세스의 메모리에만** 존재하고 DB 에 애초에 기록되지 않는다.
> 대시보드가 나중에 주워올 방법이 없다.

**설계 결정**

| 결정 | 이유 |
|---|---|
| append-only | `detections` UPSERT 사고를 반복하지 않는다 |
| zlib 압축 | 건당 1~4KB. 실측 압축률 **0.567** → 하루 100건이면 **연 53MB** |
| 이상거래만 캐시 | 정상 거래는 LLM 도 안 돌았고 남길 근거도 없다 |
| **저장 직전 재마스킹** | 심층 방어. `dashboard._save_detection_to_db` 는 원본을 넣으므로 어느 경로로 들어와도 평문이 안 쌓이게 (**DB 파일 바이트 검사로 검증**) |
| 실패해도 탐지 계속 | 캐시는 부가 기능. 저장 실패로 알림이 막히면 본말전도 |
| 판정된 건은 보존 | `prune()` 이 나이로 지울 때 `alert_review` 에 판정이 달린 거래는 제외 |
| **당시 환경 동봉** | 임계값이 핫 리로드되므로, 지금 화면의 `th_review` 는 이 판정의 기준이 아닐 수 있다 |

**정직한 안내** — 훅을 붙이기 전 탐지분은 **복원 불가능**하다.
로그 화면이 그 사실을 명시적으로 안내한다 (조용히 빈 화면을 보여주지 않는다).

## C-5. 🔴 마스킹본으로 재예측하면 "성공"하지만 무의미하다

**증상**
저장된 거래를 지금 모델로 다시 돌리는 재검증 기능이, **예외 없이 결과를 낸다.**
그런데 그 숫자에 의미가 없다.

**재현 조건**
워처가 `detections.raw_json` 에 넣는 것은 **마스킹본**이다 (`detect_service.py:713`).
그 데이터로 재예측할 때.

**원인 진단**
마스킹이 값의 **의미를 파괴**한다.

```
Account_account_number   oVZASOzgcm      → oV******cm     (인코더가 모르는 값)
IP_Address               171.237.22.26   → 171.237.*.*
Location                 강원도 고성군 ... → 강원도 ***
Customer_Birthyear       1980            → 1980년대        (수치 → 문자)
```

전처리는 이것들을 **조용히 기본값으로 메우고**, 예측은 "성공"한다. 숫자에 의미가 없을 뿐이다.

**실측 — 마스킹 레벨별 훼손도**

| 레벨 | 판정 | 훼손 컬럼 | 치명 컬럼 |
|---|---|---|---|
| `basic` | ⚠️ warn | 3 | 0 |
| `standard` ← **워처 기본값** | 🚫 **block** | 7 | **4** |
| `strict` | 🚫 block | 8 | 5 |

**해결**
`mask_damage()` 가 **모델 로드 전에** 막는다 (무거운 로드도 회피).
우회 경로는 하나 — `recheck(..., features=원본행)` (`inbox/` 원본 CSV 사용).

> **마스킹은 옳은 결정이었다.** 문제는 마스킹한 데이터를 원본처럼 재사용한 것이다.
> 그리고 그 오용이 **예외 없이 그럴듯한 숫자를 낸다**는 것이 진짜 위험이다.

## C-6. 🔴 더미 모드 → 담당자 판정 → 재학습 = 폐쇄 오염 루프

**증상 (발생 전 차단)**
모델 로드 실패 시 `MLClassifier` 는 `_dummy_predict()` 로 폴백한다 —
**15% 확률 랜덤 사기 판정**(`ml_classifier.py:295`)인데 반환값만 봐선 진짜와 구분이 안 된다.

**재현 조건**
```
더미 난수 판정 → 담당자가 "오탐" 판정 → export_training_labels() → 재학습
```

**원인 진단**
각 단계는 정상적으로 동작한다. 문제는 **연결됐을 때**다.

1. 모델 파일이 없거나 깨져서 더미 모드
2. 화면에는 정상적인 판정처럼 보인다 (유형 · 위험점수 · 확률)
3. 담당자가 성실하게 "이건 오탐" 판정
4. 그 판정이 재학습 라벨로 내보내진다
5. **가짜 데이터가 모델을 오염시키는 폐쇄 루프**

**해결**
- 더미를 감지하면 **재검증 자체를 거부**한다. 폴백하지 않는다.
- `DetectService` 의 `allow_dummy=False` 정책 승계
- `load_guarded(path)` → 더미면 `ok=False`
- 로그에 `→ 더미 모드` 를 명시적으로 남긴다 (트러블슈팅 표 1행)

> **"에러를 내지 말고 계속 돌아가게 하라"는 원칙이 위험해지는 지점**입니다.
> 폴백이 조용하면, 잘못된 값이 시스템 안쪽으로 흘러 들어갑니다.

## C-10. 🟠 주입 HTML 버튼은 못 쓴다 — iframe realm 파괴

> **같은 함정을 두 번 밟았습니다** (경보 카드 · 온보딩 모달).

**증상**
경보 카드가 **안 사라지고**, 카드의 버튼도 **안 눌린다.**

**재현 조건**
`components.html` / `st.iframe` 안에서 DOM 을 만들어 `window.parent.document.body` 에 append 하고,
그 DOM 에 `onclick` 과 `setTimeout` 을 다는 방식.

**원인 진단**
`components.html` 은 **iframe** 을 만든다. 카드 DOM 은 부모 문서에 붙였지만,
`onclick` 클로저와 `setTimeout` 은 **iframe 의 실행 컨텍스트(realm) 소유**다.

Streamlit 은 리런마다 컴포넌트 iframe 을 **파괴·재생성**한다. 그 순간:

| 대상 | 결과 |
|---|---|
| 예약된 `setTimeout` | **취소** → 카드가 영원히 안 사라짐 |
| `onclick` 이 참조하던 함수 | realm 이 죽음 → **버튼 무반응** |
| 카드 DOM | 부모에 있으니 **화면에는 그대로 남음** |

정확히 신고된 증상이다.

**1차 수정도 실패했다** — 컨트롤러를 부모 realm 으로 주입해 봤지만
실제 브라우저에서는 동작하지 않았다. CSP·샌드박스 조합에 따라 주입 자체가 막히면 방법이 없다.

**최종 해결 — 클릭이 필요한 것은 전부 `st.button`(네이티브 위젯)으로**

| | 이전 | 현재 |
|---|---|---|
| 카드 | 주입 HTML (우상단 고정) | **네이티브 위젯** (탭 위, 어느 탭에서든 보임) |
| 버튼 | iframe realm `onclick` | **`st.button`** |
| 자동 소멸 | JS `setTimeout` | **타임스탬프 비교** (리런마다 재계산) |
| 상태 | DOM | `st.session_state["_ops_active_alerts"]` |

**대가** — 우상단 고정이 아니라 페이지 상단에 놓인다.
**버튼이 실제로 눌리는 것**과 바꿨다.

JS 는 클릭이 필요 없는 것(소리 · 데스크톱 알림)에만 남겼다.

**근거** — [`PATCH_NOTES5.md`](../PATCH_NOTES5.md) v22 §0 · v23

## C-11. 🔴 임계값 슬라이더가 `0.005` 를 만들 수 없었다

> **이 한 건이 나머지 8건의 사용성 점검을 정당화했습니다.**

**증상**
튜닝 탭을 열고 **`[적용]` 만 눌러도** 임계값이 `0.005` → `0.01` 로 **2배**가 된다.

**재현 조건**
임계값 슬라이더의 `step=0.01`. 표현 가능한 값은 `0.00 / 0.01 / 0.02 …`
→ **현재 운영값 `0.005` 는 격자 위에 없다.**

**원인 진단**
슬라이더가 현재값 0.005 를 표시할 수 없으니 가장 가까운 격자값으로 스냅한다.
`[적용]` 을 누르면 그 스냅된 값이 저장된다.

**왜 안 잡혔나 — 예외가 안 난다.**
저장도 되고 로그도 남는다. **경보가 절반으로 줄 뿐이다.**
임계값이 2배가 되면 알림이 줄어드는데, 그건 "오늘 조용하네" 로 보인다.

**해결**
오른쪽에 `정확한 값` 숫자 칸(`step=0.001`, `%.4f`)을 붙이고 슬라이더와 양방향 동기화.
**적용값은 항상 숫자 칸**이다 (슬라이더는 대략 위치를 잡는 용도).

**함께 붙인 것 — 되돌릴 수 없는 동작에 확인 카드 7곳**

| 동작 | 확인 카드가 보여주는 것 |
|---|---|
| 임계값 저장 | 현재→변경 대조표 · 알림/놓친사기 증감 · 신뢰불가 구간 경고 · 결정 근거 |
| 발송 6곳 (단건·AI·일괄 × Slack·Email) | 수신처 · 마스킹 레벨 · **본문 미리보기** |

구현은 **한 벌**이다 — `_send_ask(slot, channel, body, **kw)` / `_send_confirm(slot)`.
6곳이 같은 코드를 쓴다. **v27(A2)의 교훈** — 같은 화면이 여러 벌이면 한쪽만 고쳐진다 ([`03b` #B-11](03b_issues_dashboard_pipeline.md)).

## C-29. 🔴 인증이 없다 — URL 을 아는 누구나 조회·발송할 수 있다

**증상**
ngrok URL 을 아는 사람은 **누구나** 거래내역을 조회하고 이메일·Slack 을 발송할 수 있다.
판정도 찍을 수 있다.

**재현 조건**
`start_fds_all_ops.bat` 로 전체 스택을 띄우면 ngrok 이 관제 콘솔(:8502)을 공개한다.
**인증 레이어가 없다.**

**영향**
- 개인정보(거래내역 · 계좌 · 고객명)가 담긴 화면이 URL 만으로 열린다
- 외부인이 임의로 이메일·Slack 을 발송할 수 있다
- 판정 권한 분리도 없다 — 누구나 정탐/오탐을 찍을 수 있고, 그 판정이 재학습 라벨이 된다

**필요한 조치**
```bash
ngrok http --basic-auth "user:password" 8502
```
또는 앱 레벨 로그인.

**왜 아직 안 됐나**
발표·시연 목적의 임시 공개였고, 운영 전환 전에 반드시 붙여야 하는 항목으로 남겨 뒀다.
README 최상단에 🔴 경고로 명시돼 있다.
