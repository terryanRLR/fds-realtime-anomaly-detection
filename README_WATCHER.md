### 두 대시보드의 역할 분담

|  | `dashboard.py` :8501 | `ops_dashboard.py` :8502 |
|---|---|---|
| 목적 | **분석·검증** — 모델 성능, 합성 데이터 | **운영** — 알림 판정, 임계값 조정 |
| 데이터 | 검증셋 (test.csv · parquet) | **라이브 DB** (`fds_results.db`) |
| 수명 | "열어서 본다" | **"켜 둔다"** |
| 사용자 | 분석가·발표자 | **관제 담당자** |

두 앱은 같은 DB·같은 판정 엔진을 쓰고, v20부터 **탐지 결과 UI도 공유**한다
(`pipeline/detect_ui.py`).

> ⚠️ 관제 콘솔은 **워처가 도는 그 PC에서** 열어야 한다. `fds_results.db`가 로컬 파일이라
> 다른 서버에서는 워처 상태가 보이지 않는다.

**핵심 원칙: 판정 로직은 `pipeline/detect_service.py` 한 곳에만 존재한다.**
워처·대시보드·(향후) MCP가 전부 이 하나를 호출한다. 복붙해서 두 벌이 되면
"대시보드는 정상인데 알림은 왔어요" 사고가 난다.

```cmd
start_fds_team.bat        (더블클릭)
```

창 4개가 뜬다: **llama.cpp / FDS watcher / Streamlit / ngrok**

```
[0/6] ngrok 스테일 세션 정리
[1/6] 경로·프로그램 점검
[2/6] 헬퍼 스크립트 작성

[5/6] Streamlit 시작
```

## 4-2. 관제 콘솔 (`ops_dashboard.py`) — 판정 루프

> 실무자용 상세 매뉴얼은 **`ops_dashboard_사용설명서.md`** 를 보세요.
> 여기서는 운영자가 알아야 할 최소한만 다룹니다.

### 왜 별도 앱인가

워처는 "알림을 만드는 것"까지만 한다. **그 알림이 맞았는지 틀렸는지 아무도 기록하지
않으면** 임계값을 조정할 근거가 영원히 생기지 않는다(`batch_analyzer.py:491`의 TODO가
그것이었다). 관제 콘솔은 그 루프를 닫는다.

```
워처 탐지 → 알림 발송 → 담당자 판정(정탐/오탐) → 오탐 분석 → 임계값 재조정
   ↑                                                            │
   └────────────────────────────────────────────────────────────┘
```

### 실행

```bat
run_ops_dashboard.bat          :8502 고정 (dashboard.py = :8501)
```

화면 우상단 `🔌 ops_dashboard.py · :8502` 배지로 어느 앱인지 확인한다.
**두 탭에서 같은 배지가 보이면 포트 충돌** — 둘 중 하나는 실제로 안 떠 있다.

첫 실행 시 사용 안내 팝업이 뜬다(`.ops_onboarded` 마커로 1회만).
사이드바 `🎓 사용 안내 다시 보기`로 언제든 재호출.

### 여러 명이 교대로 쓸 때 (v20)

1. **각자 검토자 이름을 다르게** 설정 — 사이드바 `🛡 관제 설정 → 검토자`
   판정 기록·잠금·임시저장이 전부 이 이름으로 묶인다
2. `🔒 동시 판정 잠금`을 켜 둔다(기본 켬)
3. `🔒 다른이름`이 보이면 **먼저 확인**하고 넘어간다

```
alice 가 TXN_001 에 입력 시작
   → alert_claim 에 (TXN_001, alice, 지금) 기록
   → bob 화면에 "🔒 alice 님이 3분 전부터 검토 중입니다"

alice 저장          → 잠금 자동 해제 + 임시저장 삭제 (같은 트랜잭션)
alice 브라우저 닫음  → 15분 후 자동 만료 → bob 이 가져갈 수 있음
```

> **협조적 잠금**이다. 물리적으로 막지 않는다 — `🔓 잠금 무시하고 내가 검토`로 넘어갈 수 있다.
> DB 레벨 강제 잠금은 워처의 쓰기까지 물릴 수 있어 위험하다.

**임시저장**은 판정·사유·메모를 입력 즉시 DB에 쓴다. 새로고침해도 남는다.
사람마다 따로 보관되므로 같은 알림을 둘이 봐도 서로의 메모를 덮어쓰지 않는다.

### SLA (v20)

알림이 뜬 뒤 판정까지 약속한 시간(사이드바에서 조정, 기본 30분).

- 트리아지 상단 KPI: 대기 / SLA 초과 / 임박 / 최장 대기
- 알림 헤더: `🔴 0.930 · J 대포통장 · TXN_8821 · ⏱ 1시간 30분`
- **기본 정렬이 '대기순'** — 점수 높은 건은 이미 누가 봤을 확률이 높고,
  방치된 건은 아무도 안 봤다

### 교대 인수인계 (v20)

근무 **시작**에 앞사람 메모를 읽고, **끝**에 남길 것을 적는다.
저장 시 당시 요약 스냅샷(유입·판정·미처리·최장대기·판정자별)이 함께 보관되므로,
나중에 숫자가 바뀌어도 "그날 상황"이 남는다. `.md`로 내려받아 메신저에 붙일 수도 있다.

### 자동 발송 (v20)

사이드바 `📨 알림 채널`에서 켠다. **되돌릴 수 없는 동작이라 기본 OFF**.

| 등급 | 조건 | 나가는 채널 |
|---|---|---|
| `none` | 1차 임계값 미만 | 발송 안 함 |
| `review` | 1차 ≤ 위험도 < 2차 | **Slack만** |
| `confirm` | 2차 이상 | Slack + Email |
| `single` | 이중 임계값 OFF | 기존 단일 동작 |

나간 것은 자동·수동 가리지 않고 **🩺 진단 → 📤 발송 감사 로그**에 남는다
(누가·언제·어디로·어떤 마스킹). 외부로 나간 것은 회수할 수 없기 때문이다.

## 5. 임계값 조정

**우선순위: CLI 명시 > `watcher_config.json` > `.env` > 기본값**

- **방법 A** 대시보드 세션5 → 워처 상태 → ⚙️ 설정 → 슬라이더 → 저장 (5초 내 반영)
- **방법 B** `watcher_config.json` 직접 수정 (재시작 불필요)

### 현재 값과 근거 (2026-08-05 · 기대비용 기반)

```
th_review  = 0.005   1차 · Slack만 (검토 요청)
th_confirm = 0.90    2차 · Slack+Email (확정 통보)
```

**성능 지표만으로는 임계값을 정할 수 없다.** 미탐(FN)과 오탐(FP)은 성격이 다른 비용을
만들기 때문이다. 그래서 기대비용으로 결정한다.

```
기대비용 = 미탐 건수 × 1,700만원  +  오탐 건수 × 5만원
           (보이스피싱 건당 평균 피해액)   (고객 불편·검토 대응비, 보수적 상한)
```

`X_va.parquet` 23,860행 / 사기 258건(1.08%) 기준:

| 임계값 | 미탐 | 기대비용 | Macro-F1 | 판정 |
|---|---|---|---|---|
| 0.001 | 19 | 3.48억 | 0.43 | ✗ 제약 위반 |
| 0.003 | 23 | 4.05억 | 0.52 | ✗ 제약 위반 |
| **0.005 (채택)** | **27** | **4.62억** | **0.603** | ★ 제약 하 최소 |
| 0.01 | 31 | 5.29억 | — | |
| 0.10 (이전) | 44 | 7.48억 | — | |
| 0.45 (최초 추측) | 57 | 9.69억 | — | |

**순수 비용최소화의 함정** — 비용만 보면 임계값을 0 근처로 밀게 되는데,
그러면 전량 의심처리가 되어 모델이 붕괴한다(임계값 0 → 비용 11.8억으로 오히려 증가).
그래서 **Macro-F1 ≥ 0.6 제약** 하에서 비용을 최소화했다.

> ⚠️ **이 제약값의 근거를 반드시 함께 설명할 것.** 최종값을 정한 것은 비용이 아니라
> 이 제약이다. 0.6은 `model_meta.json`의 기준선 0.6138을 지키는 값이다.
> 제약을 낮추면 더 싼 임계값이 선택되므로 "왜 0.6인가"에 답할 수 있어야 한다.

**결론의 견고성** — 오탐 1건이 **425만원**은 되어야 이전 값(0.10)이 이긴다.
가정(5만원)의 85배다. 어떤 시나리오를 넣어도 뒤집히지 않는다.

**⚠️ 단정하지 말 것** — 0.005 / 0.008 / 0.01의 비용 차이는 미탐 5건 이내다.
사기 258건 표본에서 이 정도는 분산 범위일 수 있다.

**FN 단가 고정 가정의 한계** — 유형별 실제 피해액은 `i`형 8,097만원 ~ `h`형 347만원으로
**23배** 차이가 난다. 임계값이 낮아질수록 고정 단가와의 오차가 커진다(최대 36%).
다만 실제 금액으로 계산해도 절감 방향은 같다(0.10 8.38억 → 0.005 5.06억).

재측정: `python -m tools.threshold_report --daily 300 --fn-cost 1700 --fp-cost 5 --min-macro-f1 0.6`

### 임계값의 실제 영향력은 작다

워처 규칙은 `위험점수 ≥ 임계값` **OR** `예측 유형이 사기`다.
모델이 argmax로 사기라 부른 **200건은 임계값과 무관하게 항상 알림**이 간다.
임계값이 좌우하는 건 *"유형은 정상인데 점수가 애매한"* 20~30건 구간뿐이다.

OR 조건은 **의도적**이다. 무인 경로에서 미탐은 되돌릴 수 없기 때문.

### 재현율 숫자가 두 개인 이유

| 지표 | 의미 | 값 |
|---|---|---|
| 탐지 재현율 | 사기를 **사기로** 잡았나 (유형 무관) | 82.9% |
| `verify_bundle` 재현율 | 사기를 **정확한 유형으로** 맞췄나 | 53.5% |

알림 관점에선 앞, 모델 성능 관점에선 뒤가 맞다.

## 6. 워처 시작·중지 버튼 (기본 잠김)

`.env` 에 다음을 추가해야 버튼이 활성화된다:

```
FDS_ALLOW_WATCHER_CONTROL=1
```

**왜 기본으로 열지 않았나.** 대시보드는 ngrok / Streamlit Cloud로 공유된다.
버튼이 열려 있으면 **URL을 아는 누구나 이 PC의 프로세스를 켜고 끌 수 있다.**
"기본 열림 + 나중에 닫기"는 까먹으면 사고지만, "기본 닫힘 + 필요할 때 열기"는 안전하다.

**중지는 강제 종료가 아니다.** `.watcher.stop` 신호 파일을 만들면 워처가
폴링 루프에서 감지해 **현재 행을 마치고 커서를 저장한 뒤** 멈춘다.
`taskkill`로 죽이면 커서가 저장되지 않아 재시작 시 중복 처리나 누락이 생긴다.

## 7. 데드맨 스위치 (워처 사망 감지)

작업 스케줄러가 10분마다 `tools/check_watcher.py`를 돌려 하트비트를 확인한다.

**별도 상주 데몬을 만들지 않은 이유:** 감시자도 죽을 수 있다.
작업 스케줄러는 OS가 관리하므로 우리가 만든 어떤 프로세스보다 안 죽는다.

### 설치

```cmd
REM ① 발송 테스트 (일부러 다운 판정 -> Slack 오는지 확인)
python -m tools.check_watcher --stale-minutes 0 -v

REM ② 정상 판정 확인 + 상태 초기화
python -m tools.check_watcher -v

REM ③ 스케줄러 등록 (관리자 권한)
install_deadman.bat

REM ④ 즉시 1회 실행
schtasks /Run /TN "FDS Watcher Deadman"
type logs\deadman.log
```

### 동작 규칙

| 상황 | 알림 |
|---|---|
| 정상 (10분 내 폴링) | 없음 |
| 10분 이상 무응답 | 🔴 1회 → 이후 60분 쿨다운 |
| 복구됨 | 🟢 1회 후 상태 초기화 |
| 대시보드 버튼으로 중지 (`note=stopped`) | **없음** (의도적 중지) |
| `--once` 1회 실행 (`note=once`) | 없음 |
| 워처를 한 번도 실행 안 함 | 없음 |

`⑤ 의도적 중지`를 구분하는 게 중요하다. 이게 없으면 워처를 끌 때마다
"죽었어요!" 알림이 와서 금방 무시하게 된다.

### 옵션

`check_watcher.bat` 안의 한 줄만 고치면 된다:

```bat
python -m tools.check_watcher --stale-minutes 10 --cooldown-minutes 60 %*
```

`--restart` 를 붙이면 다운 시 자동 재시작한다(1시간에 3회 제한).
**처음 며칠은 붙이지 말 것.** 왜 죽는지 먼저 알아야 자동 복구가 맞는 처방인지 판단할 수 있다.

제거: `schtasks /Delete /TN "FDS Watcher Deadman" /F`

## 7-2. AI 에이전트 (대시보드 챗봇) — 액션 21개

### 무엇이 달라졌나

에이전트는 원래 **화면 스냅샷만** 보고 답했다. 그래서 워처·DB·알림에 대해 물으면
"화면에 표시되지 않았다"밖에 답할 수 없었다.
이제 매 턴마다 **DB와 설정 파일에서 조회한 사실**이 컨텍스트에 함께 들어간다.

**설계 원칙 — 사실은 파이썬이, 설명은 LLM이.**
진단(왜 알림이 안 오는가)을 LLM이 추론하게 두면 그럴듯한 오답을 만든다
(멀쩡한 워처를 죽었다고 단정하는 식). 그래서 점검은 전부 `agent_facts.py`의
파이썬 코드가 하고, LLM은 그 결과를 사람 말로 풀어줄 뿐이다.
— 이 프로젝트가 *판정은 ML, 설명은 규칙* 으로 나눈 것과 같은 이유다.

### 주입되는 사실 (매 턴)

```
── 워처(무인 감시) 현황 ──
상태 / 마지막 폴링 / 누적 폴링·행·이상거래·발송·오류 / 감시 파일별 진행도
워처 임계값 · 마스킹 · 채널 · DRY-RUN 여부
오늘 탐지 총계 · 유형별 · 최근 이상거래 5건
── 임계값 실측표 (threshold_report.csv 인용) ──
── 자가진단 (파이썬이 실제로 점검한 결과) ──
```

### 자가진단 체인 — 순서에 의미가 있다

`"왜 알림이 안 와?"` 한 마디에 아래를 순서대로 점검하고 **가장 먼저 볼 것**을 짚어준다.
위쪽이 막혀 있으면 아래는 볼 필요도 없다.

| # | 점검 | 대표 결과 |
|---|---|---|
| 1 | 워처 생존 (하트비트) | 정상 / 중지됨 / 1회 실행 / 응답 없음 |
| 2 | 감시 파일 유입 | "inbox에 처리된 CSV가 없습니다" ← 가장 흔한 원인 |
| 3 | 임계값 | 0.9 이상이면 "매우 높음", 0.05 이하면 "매우 낮음" |
| 4 | 발송 스위치 | DRY-RUN 켜짐 / 채널 전부 꺼짐 |
| 5 | 채널 설정 | SLACK_WEBHOOK_URL · SMTP 계정·수신자 |
| 6 | 로컬 LLM | llama.cpp 소켓 응답 (알림은 나가되 AI 분석이 빠짐) |
| 7 | 중복 억제 | 탐지는 됐는데 발송 이력이 없는 경우 |

CLI로도 볼 수 있다: `python -m pipeline.agent_facts`

### 액션 21개

**화면 이동·입력 (6)**
`goto_session` · `goto_s5_tab` · `goto_batch_subtab` · `set_manual_field` ·
`set_manual_flag` · `autofill_high_risk`

**실행 (2)**
`run_detection` · `run_batch`

**설정 (7)**
`set_threshold`(화면) · `select_model` · `select_dataset` · `set_eval_mode` ·
`set_pii_level` · `set_compact_mode` · `set_beginner_mode`

**발송 — 승인 게이트 (2)**
`request_send` · `cancel_send`

**🆕 워처 제어 (4)**
| 액션 | 동작 | 안전장치 |
|---|---|---|
| `set_watcher_threshold(review\|confirm, 0.30)` | 워처 임계값 변경 (5초 내 반영) | 가역이라 게이트 없음 · 변경 전 영향 수치 안내 · 감사 기록 |
| `watcher_stop(분)` | 중지 요청 (0=무기한) | 승인 카드 + Slack 통지 + 예약 재개 |

### 임계값 두 개 혼동 방지

| | 저장 위치 | 영향 |
|---|---|---|
| `set_threshold` | `st.session_state` | **대시보드 수동 탐지**만 |
| `set_watcher_threshold` | `watcher_config.json` | **워처 무인 탐지** |

슬라이더는 어느 쪽인지 눈에 보이지만 **자연어는 구분해주지 않는다.**
그래서 4개 국어 시스템 프롬프트에 *"'임계값'만 말하면 어느 쪽인지 되물어라"* 를 넣었고,
컨텍스트에도 *"워처 전용이며 화면 상단 임계값과 별개"* 를 명시한다.

### 임계값 변경은 숫자를 먼저 말한다

`threshold_report.csv`가 있으면 에이전트가 **실측표를 인용**한다. 모델을 다시 돌리지 않는다
(챗 한 턴마다 23,860행을 추론하면 대시보드가 멈춘다).

> "워처 검토 임계값을 0.10 → 0.30으로 올리면 하루 알림 2.8 → 2.6건,
> 사기 탐지 214 → 205건(9건 더 놓침)입니다. 진행할까요?"

리포트가 없으면 *"먼저 `python -m tools.threshold_report` 를 실행하세요"* 라고 안내한다.

### 승인 카드 (워처 제어 전용)

에이전트는 **요청만 남기고** 실제 실행은 세션5 워처 패널의 카드에서 사람이 승인해야 일어난다.
자연어는 *"꺼줘"* 와 *"끄면 어떻게 돼?"* 를 헷갈릴 수 있기 때문이다.
기존 발송 게이트(`_send_request`)와는 독립적으로 동작한다 — 그 코드는 건드리지 않았다.

무기한 중지(0분)를 요청하면 카드가 파란 안내가 아니라 **노란 경고**로 바뀌고
자동 재개 시간을 정하도록 권한다.

### ⚠️ 껐다가 잊어버리는 사고 — 3중 방어

데드맨 스위치는 `note=stopped`를 '의도적 중지'로 보고 조용히 넘어간다.
그래서 대화 중에 껐다가 잊으면 며칠 동안 탐지 공백이 생길 수 있다.

| 방어 | 동작 |
|---|---|
| 끌 때 Slack 통지 | "🟡 워처 수동 중지 — 요청자 · 사유 · 재개 예정" |
| 예약 자동 재개 | 워처는 꺼져 있어 스스로 못 살아난다 → **데드맨 스위치가 대신 켠다** |
| 장기 중지 상기 | 6시간 넘게 꺼져 있으면 하루 1회 "계속 꺼져 있습니다" 알림 |

예약 재개가 걸려 있는 동안에는 데드맨이 **다운 알림을 내지 않는다**(계획된 중지이므로).
사람이 먼저 켜면 예약은 자동 해제된다.

### 하지 않기로 한 것

- **에이전트가 임계값을 스스로 확정** — 근거를 대도 판단은 사람 몫
- **DB 쓰기 권한** — 조회만 (커서 삭제는 승인 카드 경유)
- **UI 등가물 없는 에이전트 전용 기능** — 에이전트가 죽으면 못 하게 된다.
  기존 액션이 전부 화면 조작인 것은 좋은 설계다. 모든 액션에 손으로 하는 방법이 있다.

## 8. 배포 방식 — 왜 NSSM을 안 쓰나

| | 런처 방식 (현재) | NSSM 서비스 |
|---|---|---|
| 시작 | 아이콘 더블클릭 | 부팅 시 자동 |
| llama.cpp | 같이 뜸 ✅ | 별도 등록 필요 |
| ngrok 공유 | 됨 ✅ | 안 됨 |
| 창 | 보임 (디버깅 쉬움) | 안 보임 |

26B 모델을 데스크톱에서 돌리고 ngrok으로 팀에 공유하는 패턴은
**"필요할 때 켜는 팀 서버"**지 24시간 무인 서버가 아니다.
워처만 서비스로 띄우면 llama 없이 돌아 **AI 분석이 계속 폴백**으로 나간다.

`service_install.bat`은 그대로 두었다. 나중에 진짜 24시간 무인이 필요해지면
llama까지 함께 서비스로 올리면 된다. 그때 런처는 `WATCHER_ENABLE=0`으로 두면
이중 실행이 방지된다. (런처가 `sc query FDSWatcher`로 자동 감지도 한다)

## 9. Streamlit Cloud 배포 시 제약

Streamlit Cloud는 **오빠 PC가 아니라 Streamlit 서버에서** 대시보드를 실행한다.

| 기능 | 로컬/ngrok | Streamlit Cloud |
|---|---|---|
| 워처 상태 패널 | ✅ | ⚠️ DB 접근 불가 → **상태 푸시로 해결** (아래) |
| 임계값 설정 저장 | ✅ | ❌ 클라우드 컨테이너에 저장(무의미) |
| 📤 inbox 전송 | ✅ | ❌ 임시 디스크로 감 |
| 워처 시작·중지 | ✅ | ❌ 자동 차단 |
| 탐지 실행(수동) | ✅ | ✅ 자체 API로 동작 |

### ☁ 워처 상태 내보내기 (v24 — `pipeline/status_push.py`)

예전에는 *"워처가 외부로 상태를 밀어주는 구조가 필요하다 — 미구현"* 이었다.
이제 워처가 폴링할 때마다 상태 스냅샷을 JSON 으로 내보낼 수 있다.

```ini
# .env — 둘 다 선택. 설정하지 않으면 아무 일도 하지 않는다(기존 동작 그대로)
FDS_STATUS_FILE=D:/공유폴더/fds_status.json        # 파일로 (OneDrive·S3 마운트·공유폴더)
FDS_STATUS_URL=https://xxx.supabase.co/rest/v1/fds_status   # 또는 HTTP POST
FDS_STATUS_HEADERS={"apikey":"...","Authorization":"Bearer ..."}
FDS_STATUS_MIN_SEC=30      # 5초 폴링마다 두드리지 않도록 최소 간격
```

대시보드 쪽에서도 같은 `FDS_STATUS_FILE` 을 설정하면, 로컬 DB 에 워처 흔적이
없을 때 그 스냅샷을 읽어 **평소와 같은 상태 패널**을 그린다(화면에 "다른 서버에서
돌고 있습니다"라고 밝힌다).

- 파일은 임시파일 → 원자적 교체 — 읽는 쪽이 반쪽 JSON 을 보지 않는다.
- **어떤 실패도 워처를 멈추지 않는다** — 상태 보고가 탐지를 죽이면 주객전도다.
- 확인: `python -m pipeline.status_push --test`

> ⚠️ 실제 클라우드 엔드포인트로는 아직 검증하지 못했다. 파일 경로와 로컬
> 연결 거부 스텁까지 확인했다(`python -m pipeline.selftest_status_push`).

## 10. 트러블슈팅

### ❌ `No module named 'lightgbm'` / 모델 로드 실패
잘못된 파이썬 인터프리터. conda 환경이 아닌 시스템 파이썬으로 실행됨.
```cmd
python -c "import sys,lightgbm; print(sys.executable)"
REM -> miniconda3\envs\qaqc_st\python.exe 여야 정상
```
> 위험한 이유: `MLClassifier`는 로드 실패 시 조용히 더미 모드로 빠져
> **15% 확률 랜덤 사기 판정**을 낸다. 그래서 워처는 이 경우 기동을 거부한다(exit 2).

### ❌ 배치 실행 시 `'곗퀜'은(는) 내부 또는 외부 명령...`
`.bat`이 UTF-8. CMD는 배치를 시스템 코드페이지(CP949)로 읽는다.
**해결:** `.bat`은 반드시 **CP949(ANSI)로 저장**, 이모지 금지.
PowerShell에선 `.\run_watcher.bat` 처럼 `.\` 를 붙인다.

### ❌ `table transactions has no column named input_mode`
기존 DB가 구버전 스키마. `detect_service._migrate_transactions()`가 기동 시
자동으로 `ALTER TABLE ADD COLUMN` 한다(비파괴적, 기존 데이터 보존).

### ❌ `--once` 인데 `0행 처리`
정상일 수 있다. 커서에 처리 완료로 기록된 파일은 다시 읽지 않는다.
전량 재처리하려면 `watch_cursor` 테이블에서 해당 경로를 삭제.

### ❌ 기동이 20초 걸리고 HuggingFace 요청 25번
`set HF_HUB_OFFLINE=1` (캐시된 KR-SBERT의 온라인 갱신 확인을 끈다) → 19초 → 5초.
`run_watcher.bat`에 이미 포함.

### ❌ Slack에 AI 분석 없이 "기본 양식으로 발송되었습니다"
llama.cpp가 꺼져 있음. `start_fds_team.bat`으로 띄우면 순서가 보장된다.
연속 3회 실패 시 서킷 브레이커가 열려 5분간 LLM을 건너뛴다(알림은 계속 나감).

### ❌ 알림이 두 번 온다
워처가 2개 돌고 있다. `.watcher.lock` 락으로 대부분 막히지만,
NSSM 서비스 + 런처를 동시에 쓰면 발생 가능. 런처의 `WATCHER_ENABLE=0`으로 해결.

### ⚠️ `.env`의 `LLAMA_CPP_URL`
`/completion` 이 아니라 **`/v1/chat/completions`** 여야 한다.
전자는 Gemma 채팅 템플릿이 적용되지 않아 출력 품질이 크게 떨어진다.

## 11. 설계 결정 기록

| 결정 | 이유 |
|---|---|
| watchdog 대신 폴링 | Windows `ReadDirectoryChangesW`는 네트워크 공유(SMB)에서 이벤트를 신뢰할 수 없다. 조용히 파일을 놓치는 게 최악. |
| 안정화 = mtime 3초 + 크기 불변 | 쓰는 중인 반쪽 파일 회피. 시간 조건이 없으면 `--once`와 재시작 직후 대기 파일을 통째로 흘린다. |
| 처리 후 파일을 안 옮김 | append 패턴이 섞여 있어 파일을 옮기면 이후 추가분을 못 잡는다. 커서로만 추적. |
| 더미 모드 기동 거부 | 무인 운영에서 랜덤 사기 판정이 새벽에 나가는 것을 방지. |
| `cloud_fallback=False` 기본 | 로컬 LLM 실패 시 미마스킹 데이터가 외부 API로 자동 전송되는 경로 차단. |
| `detections` + `transactions` 양쪽 기록 | 대시보드는 `detections`, `data_streamer`는 `transactions`를 읽는다. |
| `raw_json`에 마스킹본 저장 | 워처는 무인으로 대량 적재하므로 DB에 평문 PII가 쌓이는 위험이 크다. |
| WAL + busy_timeout | 워처와 대시보드가 같은 sqlite에 동시 접근. |
| 워처 설정과 사이드바 슬라이더 분리 | 사이드바 값은 브라우저 세션마다 다르다. 실험하다 무인 워처 기준까지 바뀌면 위험. |
| 시작·중지 버튼 기본 잠금 | 대시보드가 공유되면 원격 프로세스 제어가 된다. |
| 중지는 신호 파일 | 강제 종료는 커서를 저장하지 못해 중복/누락을 만든다. |
| 데드맨은 작업 스케줄러 | 감시자도 죽는다. OS가 관리하는 스케줄러가 가장 안 죽는다. |
| 임계값을 기대비용으로 결정 | Macro-F1만으로는 운영 판단이 불가능하다. 미탐 1건(1,700만원)과 오탐 1건(5만원)은 340배 차이 나는 비용이다. |
| 순수 비용최소 대신 제약 하 최적화 | 비용만 최소화하면 임계값이 0으로 밀려 전량 의심처리가 된다. 모델 성능 하한을 제약으로 걸어야 한다. |
| 워처를 llama 뒤에 시작 | 워처는 알림마다 LLM을 부른다. 먼저 뜨면 초반 탐지가 폴백으로 나간다. |

### AppTest 하네스로 대시보드 검증 (v20)

UI는 컴파일만으로는 아무것도 보장하지 못한다. 위젯 키 충돌·세션 순서 문제는
**실행해야만** 드러난다 (v20의 버그 8건 중 2건이 이 방식으로만 잡혔다).

```python
# 파일에 저장해 실행: python check_ui.py
import sys; sys.path.insert(0, '.'); sys.path.insert(0, 'pipeline')
from streamlit.testing.v1 import AppTest

at = AppTest.from_file("ops_dashboard.py", default_timeout=300)
at.run()
print("예외:", len(at.exception))
for e in at.exception:
    print(e.message)
print("탭:", [tb.label for tb in at.tabs[:8]])
```

> 판정 흐름을 테스트할 때는 **반드시 DB 사본**을 쓴다
> (`at.session_state["db_path"] = "복사본.db"`). 실제 DB에 테스트 판정이 쌓이면
> 오탐률 통계가 오염된다.
